## A. 生产化与可靠性

### A0 · 生产配置、密钥与单一配置源（🔴 P0，1-2d）
- **现状**：`models/database.py` 直接读取 `DATABASE_URL` 且带 MySQL 默认账号密码，而 `config.py` 的 `Settings.database_url` 使用另一套 SQLite 默认值；对象存储也存在开发用默认密钥。不同入口可能读取到不同配置，生产环境还可能带着开发默认值启动。
- **目标**：所有运行模块只从 `get_settings()` 读取配置；生产模式缺少数据库、对象存储、队列、密钥或公开地址时启动失败，不静默回退。
- **做法**：① 合并数据库配置入口，区分 `development/test/production` profile；② 开发默认值只在非生产模式生效；③ 对 `DATABASE_URL`、`S3_*`、`PUBLIC_BASE_URL`、Redis/Celery 配置做启动校验；④ `.env.example` 只给占位符，不给可误用的生产密钥。
- **验收**：生产配置缺项时启动给出明确错误；数据库模块与 Settings 的 URL 始终一致；仓库扫描不再出现可直接使用的生产默认凭据。
- **工作量**：1-2 人日。

### A1 · DB 连接池保活（🔴 P0，0.5d）
- **现状**：`create_async_engine(DATABASE_URL, echo=False, future=True)`（[database.py:44](../ml_platform/app/models/database.py#L44)）无 `pool_pre_ping` / `pool_recycle`。MySQL `wait_timeout` 关掉空闲连接后，池里残留陈旧连接 → **空闲一段时间后首个请求 500**（本项目已复现）。
- **目标**：空闲后首请求不再 500。
- **做法**：`create_async_engine(DATABASE_URL, pool_pre_ping=True, pool_recycle=1800, pool_size=10, max_overflow=20, echo=False, future=True)`；SQLite 分支忽略池参数。
- **验收**：连接空闲 > MySQL `wait_timeout` 后连续请求 200；加一条集成测试模拟断连恢复。
- **工作量**：0.5 人日。

### A2 · 部署/推理 URL 去硬编码（🔴 P0，0.5d）
- **现状**：`base = "http://127.0.0.1:8000"`（[deploy_service.py:88](../ml_platform/app/services/deploy_service.py#L88)）拼推理 URL。上云后返回给前端/调用方的 predict/result URL 全是错的。
- **目标**：部署返回的 endpoint 在任何部署环境都正确。
- **做法**：提供唯一的 endpoint builder：优先从 `settings.PUBLIC_BASE_URL` 构造含反向代理 path prefix 的绝对地址，未配置时返回相对 `/inference/...`；部署创建、列表与详情响应统一调用，不在各 service 内自行拼接。
- **验收**：本地 / docker / 云 三处部署，predict URL 均可直接调通。
- **工作量**：0.5 人日。

### A3 · 独立代码执行器沙箱 + 超时（🔴 P0，3-5d）
- **现状**：`config_exec_service` / `data_pipeline_service` 用受限 builtins（挡了 `import`），但**同步 `exec` 跑在 FastAPI 事件循环里**——用户写 `while True` 就能**卡死整个后端**；data pipeline 注入 `pd`/`np`，理论上可经其 I/O 能力摸文件系统。
- **目标**：用户代码不能阻塞主进程、不能越权访问宿主。
- **做法**：① 生产路径固定为**每次执行独立的短生命周期子进程/容器**，不把共享 `ProcessPoolExecutor` 当安全边界；② 统一 config/pipeline 两个执行入口；③ 限制 wall-clock、CPU、内存、文件大小、文件描述符、输出大小和网络，使用临时只读/最小文件系统；④ 只通过受 schema 限制的序列化结果回传，异常结构化回传并记录审计信息；⑤ 明确 Linux 容器为生产执行目标，`resource.setrlimit` 不作为跨平台保证。
- **验收**：默认超时 5 秒（可通过受限配置调整），死循环被强制终止且主 API 仍可响应；文件系统/网络访问被拒；超大输出被截断；正常 config/pipeline 仍通；并发恶意任务不会耗尽 API 进程资源。
- **工作量**：3-5 人日。

### A4 · 训练持久化（TD-1，🟠 P1；对外/多机前升为 P0，5-8d）
- **现状**：仓库已有 `celery/inprocess` scheduler 配置与部分调度抽象，但训练、调参、解释等核心路径仍存在 `asyncio.create_task` 进程内提交。backend 重启会丢失这些运行中的任务；仅配置 Celery 不等于提交、状态、取消和恢复语义已经持久化。
- **目标**：backend 重启不杀训练；worker 可横向扩展；重活不阻塞事件循环。
- **做法**：按 TECH_DEBT 已列的 6 步（5 条提交路径改 `get_scheduler().submit`、回写语义搬到 celery 回调、Optuna 切 RDBStorage、V3 logs mirror 重接线、测试加 polling、错误传播）。
- **做法补充**：先增加生产启动门禁（禁止 `inprocess`、校验 Redis/worker 可用），持久化 broker task id 与幂等键，并提供启动时 reconciliation；再逐条迁移提交、取消、重试、超时与状态回写路径。
- **触发条件**：用户报「重启杀训练」/ 单机并发 >4 / 上 GPU / 多机部署 / 对外提供多用户服务（任一命中即还债）。
- **工作量**：5-8 人日。

### A5 · auth 网关纳入仓库（🟠 P1，2d）
- **现状**：线上有 `ml_platform_auth` 鉴权网关（nginx `auth_request` + JWT），**仓库里没有**——本地/线上行为不一致，新人本地跑不出鉴权。
- **做法**：把 auth 服务源码、compose 片段、nginx 配置纳入 `docker/`；`.env.example` 补 `AUTH_*`；文档说明本地默认关/开。
- **验收**：`docker compose up` 起出带鉴权的完整栈；仓库 checkout 即可复现线上拓扑。
- **工作量**：2 人日。

## B. 评估方法学与算法可信度

### B0 · 防数据泄漏训练 Pipeline（🔴 P0，4-6d）
- **现状**：`training_service._prepare_data()` 在 `train_test_split` 前调用 `prepare_training_frame()`；该函数会基于整份数据拟合类别编码和缺失值填充值。分类/回归 trainer 又把 `X_train` 与 `X_val` 合并后做 CV。因此验证数据既影响特征转换，也进入模型选择用 CV，最终分数不是严格的未见数据评估。推理阶段还会从原始训练数据重新拟合编码规则，模型工件没有携带完整转换状态。
- **目标**：任一验证/测试样本都不参与其对应训练过程中的转换拟合或模型拟合；训练与推理使用同一份持久化转换状态。
- **做法**：① 先修正 trainer，CV 只在 `X_train/y_train` 上进行，`X_val/y_val` 只做最终评估；② 引入可序列化的 tabular preprocessing Pipeline（列顺序、缺失值策略、类别映射、目标映射），与 estimator 一并保存；③ 外层 hold-out 先切分原始行，再只在训练集拟合最终 Pipeline；④ CV/nested CV 中每个 fold 克隆并在 fold-train 内拟合 Pipeline；⑤ 旧模型工件保留兼容读取路径并标记为 legacy preprocessing。
- **验收**：测试可证明验证集新增类别/极值不会改变训练侧映射和填充值；CV split 从不包含外层 hold-out；保存后重新加载模型对同一输入得到相同预测；旧工件仍可推理或返回明确兼容错误。
- **工作量**：4-6 人日，分两批交付：先隔离 hold-out/CV，再持久化 fold-local Pipeline。
- **进度（2026-07-15）**：B0 已完成。经典 ML 的分类/回归 CV 仅使用 `X_train/y_train`，原始行先切分，每个 fold 独立拟合转换，最终 estimator、特征转换与目标编码保存为版本化自包含 joblib 工件；预测、部署、resolver/可视化、SHAP 与 MLflow 均支持新工件并保留旧 estimator 兼容路径。DL 同样改为原始行先切分，只在训练集拟合类别映射、缺失值填充、目标编码和 StandardScaler；版本化 preprocessing sidecar 与原 `.pt`/scaler 一起保存并用于直接/部署推理，无 sidecar 的旧模型继续走兼容路径。

### B1 · 调参/评估的选择偏差（🔴 P0，2-3d）
- **现状**：grid/bayesian 按 CV 选最优超参。需审计**上报的 objective_value 是否就是那份「用于选择」的 CV 分数**——若是，则存在**乐观偏差**（selection bias），模型间/策略间对比被系统性高估。trainer 用 `StratifiedKFold`（[trainer.py:35](../ml_platform/app/core/trainer.py#L35)）+ 单次 `train_test_split`（[training_service.py:93](../ml_platform/app/services/training_service.py#L93)）。
- **目标**：明确区分用于选择候选的指标与用于确认候选泛化能力的指标，最终测试集不因反复排行而成为新的选择集。
- **做法**：① 调参和模型排行只使用 train 内部的 `selection_cv_mean/std`；② 简版只对最终入选候选执行一次 sealed hold-out，产出 `final_test`，不得再用该值反复挑选；③ 需要同时评价所有策略/模型时使用嵌套 CV（外层评估、内层选参）；④ 接口、数据库和 UI 不再用含义模糊的 `objective_value` 同时代表选择分与最终分。
- **验收**：接口可区分 `selection_cv_*` 与 `final_test`；对比页明确展示当前排序依据；测试证明 final hold-out 不进入调参、CV 或候选排序；重复最终评估需生成新的评估版本并留审计记录。
- **工作量**：2-3 人日。
- **进度（2026-07-15）**：第三批已完成，经典 ML 的 selection/final 分离与任务级封存已闭环，B1 仍进行中仅因 DL。分类/回归 trainer 产出 `selection_cv_mean_*`、`selection_cv_std_*` 与 `final_test_*`；Bayesian Optuna、旧实验 rank、V3 排行榜/策略对比、SHAP Top-K 和诊断 peer rank 已统一按 selection 值选择，run DTO 同时返回 selection/final 字段来源和值，模型对比页明确显示“选择分”。V3 经典 ML 调参 run 以 `evaluation_mode=selection` 执行，trainer 不接收外层 hold-out；自动批次评估已移除，用户只能通过任务级显式“确认最终模型”打开 sealed hold-out。确认流程先持久化版本化 claim，拒绝活动 Run 和 `RUNNING` 实验（含贝叶斯 trial 间隙），完成后锁定 winner、final 指标与审计，后续批次和优化口径修改均被后端拒绝；重复请求幂等，超时 claim 不自动接管，任务生命周期锁补齐单进程 SQLite 并发边界，支持行锁的数据库承担跨进程边界。工作流与详情页共用同一确认/失败重试状态。剩余工作：DL baseline 尚未建立 selection CV 与 sealed final 的物理隔离；完成前不得把 B1 标记为完成。

### B2 · 「公平对比」升级（🟠 P1，3-4d）
- **现状**：后端 trainer 已产出 `cv_avg_*` / `cv_std_*`，但 `ComparisonVM` 把任意 `metrics` key 当可比较指标，前端没有统一的指标方向、均值/方差配对和单位语义；耗时、模型大小也未标准化。当前图表切换到非 objective 指标时，仍可能沿用任务 objective 的方向判断“最佳”。
- **目标**：让"选最优"带统计与成本依据。
- **做法**：先定义 metric registry（key、显示名、方向、单位、是否可排行、均值/方差字段）；`ComparisonVM` 只接收注册指标，并标准化 `selection_mean / selection_std / final_test / train_seconds / artifact_bytes`；对比表加成本列，柱状图叠加**误差棒（±std）**；`StrategyCompareTab` 的五数概括思路推广到模型维度；可选加成对显著性提示。
- **验收**：对比页每个模型显示 均值±方差 + 训练耗时 + 模型大小；两个接近模型能看出"差异是否稳定"。
- **工作量**：3-4 人日（后端 run 需补 duration/size 字段 + adapter/组件改）。

### B3 · 指标契约标准化（🟠 P1，1-2d）
- **现状**：`model_registry` 已标 `class_weight_support` 等能力位；但"是否支持 `predict_proba` / SHAP tree path / 部署推理 / 批量预测"这些能力标签尚未标准化（[todo.md](./todo.md) P1 已列）。
- **做法**：注册表补齐能力标签；前端按标签决定是否显示 ROC/SHAP/部署按钮（避免对不支持的模型显示无效操作）。
- **验收**：新增模型只填标签即可正确联动 UI；加 registry 契约测试。
- **工作量**：1-2 人日。

## C. 抽象收敛与技术债

### C1 · 收敛遗留实验 API 表面（🟠 P1，3-5d）

- **目标**：保留单一 `PlatformExperiment/ExperimentRun` 数据模型，退役旧 HTTP API 与前端 adapter；不设计不必要的数据搬迁。
- **做法**：先新增 V3 run explain 契约，把 `ShapView` 的 explain 触发/读取迁到 `v3RunsApi`（或 `modelingTaskApi`）；确认 `ExperimentRedirect` 之外无旧 API 消费者后，删 `platformExperimentsApi` + 旧路由。
  （前端死文件 `Experiments.jsx`/`TaskCenter.jsx` 已于 2026-07-21 删除；剩余部分是后端旧路由与前端 wrapper 的收敛。）
- **验收**：全仓无 `platformExperimentsApi` 引用；SHAP 正常；死页面删除。
- **工作量**：3-5 人日。

### C2 · domain 关联显式化（🟠 P1，2-3d）
- **现状**：run→可部署模型要从 `PlatformTask.payload_ref` **字符串解析** `train:{id}` / `dl_train:{id}`（`_resolve_domain_ref`）——约定式、脆，格式一改全断。
- **目标**：run 与其 domain TrainingTask/DLTrainingTask 用显式、可校验的 typed relation 关联。
- **做法**：先确定单一关系所有者和基数；由于 ML/DL task 位于不同表，采用 `domain_kind` + `domain_task_id` 的关联表（或两个 nullable FK + CHECK，二选一后固化），不创建无法指向两张表的伪外键；与 run 创建同事务写入，字符串解析只作为旧数据 fallback；配 migration（见 C3）。
- **验收**：新 run 直接读字段拿到 domain id；旧数据仍可解析；桥接单测覆盖两路。
- **工作量**：2-3 人日。

### C3 · 引入 Alembic migration（🟠 P1，2d）
- **现状**：schema 靠 `Base.metadata.create_all`，无正式 migration → 运行库与代码模型漂移、加列难。
- **做法**：接 Alembic，为现有 schema 生成 baseline revision；此后加列（如 C2 的 domain 字段）走 migration；CI 校验「模型与 migration 一致」。
- **验收**：`alembic upgrade head` 从空库建出完整 schema；改模型忘写 migration 时 CI 报警。
- **工作量**：2 人日。

## E. 产品与算法差异化（季度级）

### E1 · 自动化建模（🟡 P2，2-4 周）
- **契合定位**：「傻子也会训练模型」——用户给数据集 + 目标列，平台**自动推荐候选模型 + 预算内跑对照 + 给出最优**。
- **做法**：基于 model_registry 做**一键 AutoML**（按 task_type/数据规模选候选、`grid/bayesian` 预算控制：全局最大 run 数 / 单模型最大 trial / 超时 / 并发，见 [todo.md](./todo.md) P2）；提交时自动固化数据版本/哈希、split seed/fold、代码与依赖版本、参数和工件清单；产出直接进 `ModelComparison`。
- **验收**：非算法用户一键得到「已排序的多模型对比 + 可部署最优」。
- **依赖**：B0（防泄漏 Pipeline）、B1（评估口径）、A4（并发调度）。

### E2 · 集成与联合训练（🟡 P2，spec 已提）
- **现状**：混合策略 tab 已能 ML+DL 一批对照；spec 里预留了**残差网络 / 联合训练 / Stacking**。
- **做法**：在 B2「公平对比」地基上加 **Stacking/Voting 集成**（用已有 run 的预测做 meta-learner）、DL 联合训练策略作为新的 `strategy_type`（只实现策略层，不改主流程，见 [todo.md](./todo.md) P2 契约）。
- **验收**：集成模型作为一个"模型"进对比，指标可比。

### E3 · 模型 / 数据漂移监控（🟡 P2，2-3 周）
- **现状**：[todo.md](./todo.md) P4 提到漂移入口尚无。
- **做法**：先定义推理事件契约（字段白名单、脱敏/采样、保留期、project 归属、请求关联 id）并在训练时冻结基线分布；再记录线上推理输入分布，与训练集分布对比（PSI/KS），阈值告警；模型卡展示线上输入漂移。
- **验收**：部署详情页可看输入分布漂移趋势 + 告警。

### E4 · 权限 / 审计 / 项目空间隔离（🟡 P2，与 A5 联动）
- **现状**：全系统无权限（[todo.md](./todo.md) P4），多人共享互相覆盖任务。
- **做法**：在 A5 的 auth 基础上加 RBAC + 项目空间（task/dataset/deployment 归属 project）+ 操作审计。
- **验收**：多人各自空间隔离，越权被拒，关键操作留痕。

## 依赖关系（建议实施次序）

```
A0 ──► A1 A2  ──►  可验证配置并安全上云
A3              ──►  执行器可对外
B0 ──► B1 ──► B2 公平对比 ──► E1 自动化建模 ──► E2 集成/联合训练

A5(auth 入仓)  ──► E4(权限隔离)
D1(门禁) 贯穿全程
A4(TD-1) 对外/多机前完成
```

**推荐落地顺序**：① B0/B1 先修评估与推理一致性；② A0 后做 A1/A2/A3，建立生产安全基线；③ 收敛比较页指标语义、错误状态、部署护栏并补 D 类门禁；④ C3 后做 C2；⑤ 完成 A4 持久调度；⑥ C1 退役遗留 API；⑦ B2 成本/方差展示后再进入 AutoML、集成、漂移与权限隔离。

**一句话**：先确保训练结果可信且可复现，再让平台安全上云；在这两层地基上收敛 API、门禁和调度，最后扩展「自动化建模 + 公平对比 + 集成」差异化能力。
