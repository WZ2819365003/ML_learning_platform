## 1. 物理拓扑（Docker Compose 全景）

```
┌──────────────────────────────────────────────────────────┐
│              docker network: ml_platform_network         │
│                                                          │
│  nginx:80 ─┬─> frontend:3000  (静态 SPA, serve dist)     │
│            └─> backend:8000   (FastAPI / uvicorn)        │
│                    │                                     │
│                    │        worker (celery)              │
│                    │          │                          │
│         ┌──────────┴──────────┴──────────┐               │
│         ▼          ▼                     ▼               │
│     mysql:3306  redis:6379           minio:9000          │
│    (元数据 19 表) (broker + 事件)     (artifacts)         │
│                                          ▲               │
│                            minio_init ───┘               │
│                          (一次性 seed 导入)               │
└──────────────────────────────────────────────────────────┘
        ▲
        │ 唯一对外入口
   user :${PUBLIC_HTTP_PORT:-18081}

宿主机端口映射（生产加固：除 nginx 外全部绑定回环）：
  ${PUBLIC_HTTP_PORT:-18081} → nginx:80   ← 唯一对外入口
  127.0.0.1:3000  → frontend:3000  ← 仅本机调试
  127.0.0.1:8000  → backend:8000   ← 仅本机调试
  127.0.0.1:3307  → mysql:3306
  127.0.0.1:6379  → redis:6379
  127.0.0.1:9000/9001 → minio
```

> 端口回环绑定是有意的：数据库、Redis、MinIO、backend、frontend 都不应直接
> 暴露到公网，全部流量必须经 nginx。

- 编排定义见 [`docker/docker-compose.yml`](../docker/docker-compose.yml)
- 卷：`ml_mysql_data` / `ml_redis_data` / `ml_minio_data` / `ml_backend_storage` 为 named volume（backend 与 worker 共享 storage 卷）；MinIO 首次启动通过 `minio_init` 一次性把 `docker/minio_seed/` 镜像到 `ml-platform` bucket
- 网络：所有服务在 `ml_platform_network` 内通过容器名互相寻址（`mysql`、`redis`、`minio`）

### 3.2 调用约定（自上而下）

```
HTTP request
   │
   ▼
api/routes/*.py            <- Pydantic 反序列化 + 鉴权（保留位）+ 调 service
   │
   ▼
services/*.py              <- 编排：DB 事务 / 文件 IO / MinIO / 触发训练
   │  ├─> models/database.py      (SQLAlchemy async)
   │  ├─> services/object_storage (boto3)
   │  └─> core/trainer.py         (sklearn / torch)  via ThreadPoolExecutor
   ▼
async response  (Pydantic)
```

- **Routes 不直接动 DB**，永远走 service 层
- **Service 不写 sklearn/torch 调用**，分类计算下沉到 `core/`
- **Core 不调 DB / 网络**，纯函数 + 接受预处理后的 numpy/torch tensor

### 3.3 异步与同步引擎共存

`models/database.py` 同时构建 **async（aiomysql）** 和 **sync（pymysql）** 两套 engine：

- async 用于 99% 的 FastAPI handler、websocket、background coroutine
- sync 用于跑在 ThreadPoolExecutor 里的训练函数（`_run_training_sync`）—— 因为 sklearn 是同步的，在线程内每行 `await` 反弹回事件循环开销过大

`_to_sync_database_url()` 自动把 `mysql+aiomysql://` 换成 `mysql+pymysql://`、`postgresql+asyncpg://` 换成 `postgresql+psycopg2://`、`sqlite+aiosqlite://` 换成 `sqlite://`，单一 `DATABASE_URL` 变量驱动两套引擎。

## 5. 关键数据流

### 5.1 V3 训练流（baseline 策略）

```
用户在 ExperimentBatchModal 点"创建并启动"
  │
  ▼ POST /api/v3/tasks/{id}/experiments  body={strategy_type:"baseline", selected_models:[...]}
  │
  ▼ tuning_service.dispatch_experiment_batch
  │   ├─ _validate_search_space()              <- 缺空格式直接 400
  │   ├─ _expand_baseline()                    <- 每模型一条 trial
  │   ├─ 创建 PlatformExperiment + N 个 ExperimentRun (status=PENDING)
  │   └─ 创建 N 个 PlatformTask(kind=train, payload_ref="train:{run.id}")
  │
  ▼ scheduler 派发：InProcessScheduler 把每个 PlatformTask 提交到 ThreadPoolExecutor
  │
  ▼ training_service._run_training_sync (同步上下文)
  │   ├─ 读 dataset 文件 -> pandas DataFrame
  │   ├─ split / preprocess / fit (sklearn / xgboost / lightgbm)
  │   ├─ TrainingLogger.log(...)               -> training_logs 表 + WS 推送
  │   ├─ 写 metrics & feature_importances     -> ExperimentRun.metrics
  │   ├─ joblib.dump(model, /storage/models/{id}.joblib)
  │   ├─ object_storage.upload_training_artifacts(id, [model], [log, metrics])
  │   ├─ shap_service.compute_shap_summary    -> 写 metrics.shap_* + 上传 explanations/{run_id}/
  │   └─ run.status=SUCCESS, task.status=SUCCESS
  │
  ▼ leaderboard 自动重排：modeling_task.best_run_id 由 service 增量更新
  │
  ▼ 前端 RunInspector 打开
      GET /api/platform/runs/{run_id}/inspector  -> 合成 overview/context/logs/siblings
      GET /api/platform/runs/{run_id}/shap       -> shap_service 缓存 hit
      ...
```

### 5.2 grid_search / bayesian_search 差异

- **grid_search**：`_expand_grid_search` 笛卡尔积展开 search_space，所有组合一次性生成 ExperimentRun，全部并发跑
- **bayesian_search**：`_launch_bayesian` 为**每个 model 各建一个** Optuna study
  （`TPESampler`），按 `n_trials_per_model` 顺序提交 trial；每个 trial 完成后
  Optuna 用结果更新代理模型决定下一个采样点。
  **实现是完全串行的**：外层 `for model_type in selected_models` 顺序遍历，
  内层每个 trial 提交后立即 `await`。跨 model 并行在理论上可行（各 study 相互
  独立），但当前代码没有做。

  > `n_startup_trials` 随预算缩放（`_tpe_startup_trials`：约 1/3 探索，
  > 下限 3、上限 10），而不是沿用 Optuna 默认的 10。否则平台默认的
  > `n_trials_per_model=10` 会与之相等，整个预算耗在随机启动期，
  > 一次都进不了 TPE 建模阶段 —— 即"贝叶斯搜索"实为随机搜索（见 TD-5）。
  > 默认预算下现为 3 次随机 + 7 次 TPE。

  > Celery 模式下贝叶斯被 422 拒绝：study 是进程内内存态且靠 `await` 拿结果，
  > 提交给 worker 后编排无法继续。解除该限制的方案见 doc 中的 M2d 讨论。

### 5.3 SHAP 计算流

```
shap_service.compute_shap_summary(task_id, db, max_samples=200)
  │
  ▼ resolver.py 解析 id：是 V3 run / legacy training_task / orphan platform_task ?
  │   返回统一的 (task_facade, dataset, model_path)
  │
  ▼ 加载 model + 数据，取 max_samples 个采样
  │
  ▼ 三档 fallback：
  │   1. _is_tree_model(model) → TreeExplainer    (xgb/lgbm/rf/gbm/extra_trees)
  │   2. else 可 predict_proba → KernelExplainer  (50 background)
  │   3. else permutation_importance(n_repeats=5)
  │
  ▼ 全部 astype(np.float64) 序列化（numpy 2.0 防护）
  │
  ▼ 写回 ExperimentRun.metrics.shap_*  +  上传 explanations/{run_id}/shap_summary.json
  │
  ▼ 返回 {method, base_value, sample_count, feature_names, shap_values?, top_features, ...}
```

## 6. 异步执行模型

调度有两种模式，由 `SCHEDULER_MODE` 与 `CELERY_KINDS` 决定。两者共用同一套
`PlatformTask` 记录与同一个 executor 注册表，因此同一个 kind 换模式不改语义。

### 6.1 InProcessScheduler（默认）

```
业务 service
  │
  ▼ get_scheduler(kind).submit(platform_task_id)
  │
  ▼ DAG gate: depends_on 全部 SUCCESS 才放行, 否则回落 PENDING
  │
  ▼ asyncio.create_task( executor(domain_id, platform_task_id) )
       └─ 重活提交到 ThreadPoolExecutor, 不阻塞事件循环
```

特点：
- 任务跑在 backend 进程内，**backend 重启 = 运行中的任务丢失**
- `depends_on` **已生效**：DAG gate 在 `scheduler._gate_upstream` 中实现，
  上游未完成时任务停在 PENDING 并附带等待原因
- 没有定时扫描循环。提交是事件驱动的（service 调用 → submit），
  恢复由 lifespan 中的周期 sweep 负责

### 6.2 CeleryScheduler

`CELERY_KINDS` 列出哪些 kind 走 Celery（留空则全部留在进程内），
`SCHEDULER_MODE=celery` 是全局覆盖。

```
业务 service
  │
  ▼ CeleryScheduler.submit()
  │
  ▼ PlatformTask 先落库 (QUEUED, celery_task_id=NULL) —— 发布 outbox
  │
  ▼ run_platform_task_generic.apply_async(queue=...)
  │
  ▼ worker: claim_for_execution() → executor → complete_platform_task()
```

- broker = `CELERY_BROKER_URL`（默认 redis db 0），backend = db 1
- worker 命令见 `docker/docker-compose.yml`：
  `celery -A app.scheduler.celery_app worker -Q train,explain,forecast,default --concurrency=2`
- 队列常量的唯一来源是 `app/scheduler/queues.py`，`celery_app` 启动时断言两者一致
- **所有 kind 都路由到同一个 `run_platform_task_generic`**，再由 executor
  注册表分发；没有 per-kind Celery 任务

写回保证（M2c，见 `app/services/run_writeback.py`）：
- 终态由**条件 UPDATE 的 rowcount 仲裁**，`ExperimentRun` 与 `PlatformTask`
  同一事务内写入，重复投递不会产生分裂状态
- claim-before-execute：任一记录已终态则拒绝执行
- `recover_stalled_tasks` 处理"worker 执行完但终态未落库"的尾巴

> 已知限制：executor 尚无 attempt fencing。重复执行会写同一个
> `storage/models/{task_id}.joblib`，落后的尝试可能覆盖先完成者的产物。
> **生产启用 Celery train 前必须解决。**

### 6.3 同步上下文中的 DB 访问

训练函数跑在线程里，不能 await async session。模式：

```python
def _run_training_sync(task_id):
    with sync_session_factory() as db:
        task = db.query(TrainingTask).filter_by(id=task_id).first()
        # ... train ...
        db.commit()
```

`sync_session_factory` 由 `models/database.py` 提供，连接同一个 MySQL，但走 pymysql 同步驱动。

|---|---|---|---|
| `/ws/training/{task_id}` | `training:{task_id}` | training_service | progress / metric snapshot |
| `/ws/logs/{task_id}` | `logs:{task_id}` | TrainingLogger.log | level + message + extra |
| `/ws/dl/{task_id}` | `dl:{task_id}` | dl_service after each epoch | DLTrainingEpoch payload |
| `/ws/ts/{task_id}` | `ts:{task_id}` | timesfm_service | progress + interim forecast |

### 7.2 EventBus（进程内）

```python
class EventBus:
    def __init__(self):
        self._channels: dict[str, set[Queue]] = {}
    def subscribe(channel: str) -> Queue: ...
    def unsubscribe(channel: str, queue: Queue) -> None: ...
    def publish(channel: str, payload: dict) -> None: ...
```

- 每个 WS 连接 subscribe 时拿一个 `asyncio.Queue`
- publish 是 fire-and-forget，订阅者断开会自动 GC
- 多 backend 实例时这是个**进程内**的桥；要跨实例需切到 Redis pub/sub（roadmap）

## 8. 对象存储与缓存策略

### 8.1 写路径

```
training finishes
   │
   ▼ joblib.dump → /app/storage/models/{id}.joblib   (本地热缓存)
   │
   ▼ object_storage.upload_file(local, "models/{id}.joblib")  (MinIO 持久层)
   │
   ▼ TrainingTask.model_path = local 路径   (DB 记录)
```

### 8.2 读路径（部署 / 推理）

```
deploy_service.load_model(task_id)
   │
   ▼ if local file exists  → joblib.load(local)
   │   else  → object_storage.download_object_bytes("models/{id}.joblib") → BytesIO → joblib.load
```

> 这是简单的两层缓存：本地 disk 是"热"，MinIO 是"温"。重启容器后本地丢，下次推理触发懒加载。

### 8.3 SHAP 缓存

```
GET /api/platform/runs/{id}/shap
   │
   ▼ 先看 ExperimentRun.metrics.shap_* 是否齐全
   │     齐全 → 直接序列化返回（不重算）
   │
   ▼ 否则 → object_storage.download_object_bytes("explanations/{id}/shap_summary.json")
   │     存在 → 解析返回
   │
   ▼ 否则 → shap_service.compute_shap_summary（重算 + 回写两层）
```

- 装 `requirements.txt` 全量依赖（含 numpy 2.0 + shap 0.46.0）
- COPY `ml_platform/` 进 `/app`
- entrypoint：`uvicorn app.main:app --host 0.0.0.0 --port 8000`

### 9.3 前端镜像构建

[`docker/Dockerfile.frontend`](../docker/Dockerfile.frontend)：
- base：`node:18-alpine`
- `npm ci` → `npm run build`（Vite，输出 `dist/`）
- runtime：`serve -s dist -l 3000` —— SPA-only，不代理 `/api`

### 9.4 Nginx 反向代理

[`docker/nginx.conf`](../docker/nginx.conf) 关键 location：
```
location /api/  { proxy_pass http://backend:8000;  ... }
location /ws/   { proxy_pass http://backend:8000; proxy_set_header Upgrade $http_upgrade; ... }
location /      { proxy_pass http://frontend:3000; ... }
```

这是 v3.2.4 的关键决策：**前端容器纯 SPA**，所有 `/api/*` 与 `/ws/*` 由 nginx 转后端，避免直连 `:3000` 时 axios 把 `/api/*` 路由到前端 serve 进程返回 index.html 引发的"text is not JSON" 崩溃。

### 9.5 版本与发布

- 代码版本：`ml_platform/app/main.py::version` + `ml_platform_web/package.json::version` 必须一致
- 测试报告必须记录 git commit、Docker image digest、`/health.version`，避免本地代码与运行镜像版本错位
- 发布流程：本地测试通过 → commit → `git tag -a v3.x.y -m "..."` → `git push origin main && git push origin v3.x.y`
- 远程历史：仅保留 `main` 分支，研发轨迹通过 tag 沉淀

## 11. 安全与多用户

> 当前版本是**单管理员**架构：有登录与鉴权，但只有一个账号，没有多用户、
> 没有 RBAC、没有数据隔离。这是有意的边界 —— 演示与团队内部使用场景。

已实现（`app/core/auth.py` + `app/api/routes/auth.py`）：
- 密码用 PBKDF2-SHA256（60000 轮）校验，令牌为 HMAC-SHA256 签名的自包含串
- 刻意不引第三方依赖：不用 JWT 库，只用标准库 `hashlib` / `hmac`
- `main.py` 的 `auth_guard` 中间件拦截全部 `/api/*`，白名单只有 `/api/auth/login`
- `AUTH_ENABLED` 控制开关：开发/测试默认关闭；**生产强制开启** ——
  `is_production and not auth_enabled` 会直接拒绝启动

仍缺的加固路径：

| 项 | 当前 | 加固方案 |
|---|---|---|
| 多用户 | 单账号 | 用户表 + `owner_id` 列；service 层带 `current_user.id` |
| 授权 | 全有或全无 | RBAC 角色；row-level scope |
| 数据隔离 | 无 | MinIO 按 `users/{uid}/` 前缀 |
| 凭证 | `.deploy_secrets`（chmod 600，不入库） | Docker secrets / Vault |
| HTTPS | 无（nginx 只监听 HTTP） | nginx 装 cert（Let's Encrypt） |
| 审计 | TrainingLogger 是事件流，但无 actor | 在 PlatformTask 加 `requested_by` |
